# Database Layer — DuckDB

Diego Desktop Assistant uses **DuckDB** as its embedded database engine. This document
covers DuckDB-specific design decisions, SQL dialect differences, and migration notes.

---

## 1. Why DuckDB (not SQLite / PostgreSQL)

| Feature              | DuckDB                          | SQLite / PostgreSQL            |
|----------------------|---------------------------------|--------------------------------|
| Embedding storage    | Native `FLOAT[]` array type     | BLOB / extension required      |
| Analytical queries   | Columnar, vectorized execution  | Row-oriented                   |
| Zero-config          | Single file, no server          | SQLite: single file; PG: server |
| Python integration   | `duckdb` pip package            | `sqlite3` / `psycopg2`         |

---

## 2. DuckDB-Specific SQL

### 2.1 Auto-increment — Sequences + `nextval()`

DuckDB does **not** support PostgreSQL's `SERIAL` / `BIGSERIAL` pseudo-types,
`GENERATED BY DEFAULT AS IDENTITY`, or `AUTO_INCREMENT`.

The DuckDB-native approach uses **sequences** with `nextval()` as a table function
inside `INSERT ... SELECT`:

**✅ Correct (DuckDB-native):**

```sql
CREATE SEQUENCE IF NOT EXISTS seq_intents START 1;

CREATE TABLE intents (
    id INTEGER PRIMARY KEY,
    name VARCHAR NOT NULL
);

INSERT INTO intents
SELECT nextval('seq_intents'), 'my_intent'
RETURNING id;
```

**❌ Wrong (PostgreSQL-ism):**

```sql
CREATE TABLE intents (
    id SERIAL PRIMARY KEY,          -- PostgreSQL only
    name VARCHAR NOT NULL
);
```

### 2.2 Returning generated IDs — `INSERT ... RETURNING`

Instead of calling `lastval()` or `last_insert_rowid()`, use DuckDB's `RETURNING`
clause to fetch the auto-generated ID in a single round-trip.

**✅ Correct (DuckDB-native):**

```python
result = conn.execute("""
    INSERT INTO intents
    SELECT nextval('seq_intents'), ?, ?
    RETURNING id
""", [name, description]).fetchone()
return result[0]
```

**❌ Wrong (PostgreSQL-ism):**

```python
conn.execute("INSERT INTO intents ... VALUES (nextval('seq_intents'), ...)")
result = conn.execute("SELECT lastval()").fetchone()   # PostgreSQL only
```

### 2.3 Upsert — `ON CONFLICT ... DO UPDATE`

DuckDB supports the standard `ON CONFLICT` syntax (same as PostgreSQL and SQLite).

```sql
INSERT INTO user_preferences
SELECT nextval('seq_user_preferences'), ?, ?
ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value,
                                updated_at = CURRENT_TIMESTAMP
```

### 2.4 Array types — `FLOAT[]`

DuckDB has native array support. Embeddings are stored as `FLOAT[]` columns and
passed as Python lists.

```python
emb_list = embedding.tolist()  # numpy array -> Python list
conn.execute("INSERT INTO intent_examples SELECT nextval('seq_intent_examples'), ?, ?, ?", [intent_id, text, emb_list])
```

## 3. What Was Removed / Replaced

| Old (PostgreSQL-style)              | New (DuckDB-native)                        |
|-------------------------------------|--------------------------------------------|
| `SELECT lastval()`                  | `INSERT ... RETURNING id`                  |
| `SELECT id FROM <table> WHERE ...`  | `INSERT ... RETURNING id`                  |
| Manual `id` column in `VALUES`      | `SELECT nextval('seq_<table>'), ...`       |
| `last_insert_id()` / `last_insert_rowid()` | `INSERT ... RETURNING id`           |

Sequences (`CREATE SEQUENCE`) are retained because they are **native DuckDB** —
they are not a PostgreSQL compatibility hack. DuckDB's `nextval()` is a table
function, not a scalar function, which is why it appears in `SELECT` clauses
rather than `VALUES`.

## 4. Migration from Old Schema

If you have an existing `data/Diego.duckdb` file created with the old PostgreSQL-style
schema (sequences + `nextval`), the schema is **already compatible** since DuckDB
uses the same sequence mechanism. Only the ID retrieval pattern changed.

### Option A — Delete and recreate (clean slate)

```bash
rm data/Diego.duckdb data/Diego.duckdb.wal
```

The store will recreate all tables with the correct schema on next startup.

### Option B — Keep existing data

The existing tables and sequences are compatible. No migration needed.

---

## 5. DuckDB 1.x Compatibility

All SQL in this codebase targets **DuckDB 1.x** (tested with v1.5+). Key features used:

- `CREATE SEQUENCE IF NOT EXISTS` (v0.3.2+)
- `nextval('seq')` as a table function (v0.3.2+)
- `INSERT ... RETURNING` (v0.3.2+)
- `ON CONFLICT ... DO UPDATE` (v0.3.2+)
- `FLOAT[]` array type (v0.3.2+)
- `CREATE TABLE IF NOT EXISTS` (v0.3.2+)

No PostgreSQL compatibility extensions (`pg_compat` or similar) are loaded or required.

## 6. Testing

Integration tests live in `tests/test_duckdb_store.py`. Run them with:

```bash
pytest tests/test_duckdb_store.py -v
```

Each test creates an isolated DuckDB database in a temporary file, runs operations,
and cleans up. No external database server is needed.
